# Open-core

This entry says what "open core" means as a business model, where the name comes from, and where sources differ on its limits. The differences concern whether the paid code is visible, who devised the model, whether the term has a definition and whether the model helps open source.

## Definition

In an open-core business model a vendor publishes a core product as open source and sells more around it [1][2]. The Open Core Ventures handbook, which advocates the model, says open-core companies "provide an open source core product and a commercial, source-available premium product" [2]. Andrew Lampitt, credited with the term [2], described a dual licence whose commercial side is a superset: it "offers premium product features that you will not see in the GPL license" [1].

## How it changed

- **20080829.** Lampitt proposes renaming one dual-licence strategy, "Commercial Extensions", as "open-core licensing", to remove the "bait and switch" controversy. His terms: a GPL core; a fee to embed it in closed source; a subscription with indemnity, support and extra features; paid services [1].
- **20101019.** Kuhn writes that "Open Core" "doesn't really have a well-defined meaning" and treats it as proprietary relicensing that harms software freedom [3].
- **20250402.** Zep stops maintaining Zep Community Edition: its open-core strategy meant two products with "design choices in one limiting the other", and the open one was under-invested. The repository stays under Apache 2.0 without updates. The post was updated 20260603 (first-party) [4]. See [Graphiti](../projects/graphiti.md).
- **Undated.** The Open Core Ventures handbook sets three criteria: built on open source developed alongside the commercial product, proprietary intellectual property, and all code source-available [2].

## Where sources disagree

**Is the paid code visible?** Lampitt leaves "viewable or closed source" for the extras open to debate [1]; the handbook requires all code to be source-available [2].

**Who made it?** The handbook credits Lampitt with the term [2]. A note added to his post on 20080831 credits Barry Klawans and Paul Doscher of Jaspersoft with devising the model, including "viewable code" for the extras [1].

**Is there a definition?** Kuhn doubts it, though he says Matt Aslett calls Lampitt's definition canonical [3]. Zep describes a "common practice in open-core of intentionally limiting features to drive users toward paid products" and says it was uneasy with it [4].

**Is it good for open source?** The handbook calls it "a way to sustain open source" [2]; Kuhn finds it harmful to software freedom [3].
