The numbers in brackets refer to the one list in [Instruments evidence: sources](instruments-sources.md). ## The metering gateway

A small local HTTP proxy that every hosted [large language model](../../index/large-language-model.md) call of an experiment passes through. It does three things the third-party builders cannot do themselves [3]:

1. It writes the provider's own usage fields into one common record, so a cost is measured, not estimated.
2. It refuses a call that could take spend past a cap, before anything is forwarded.
3. It keeps the real key. The code under test holds a dummy key and the gateway's address. The gateway reads the key itself, from its own environment or, since version 1.1.0, from a file only its owner can read.

It uses the standard library only, needs Python 3.11 or newer, and binds `127.0.0.1` and nothing else [3]. Its version at `b24484e` is 1.3.0 (the code is as at `c960df7`). Stages B to D ran on 1.2.0, and no real provider has met 1.3.0 [57][58][63].

### What it records

One JSON line per call, written when the call ends. Money is a decimal string, never a float. Request bodies are not in this file [3].

| Field | Meaning |
|---|---|
| `input_tokens` | All prompt [tokens](../../index/token.md), cached ones included. For Anthropic it is input plus cache read plus cache creation |
| `output_tokens` | Completion tokens; null when the provider gave no usage |
| `cached_input_tokens`, `cache_creation_input_tokens` | Cached prompt tokens (reads); cache writes: Anthropic's `cache_creation_input_tokens` and, from 1.3.0, OpenAI's `prompt_tokens_details.cache_write_tokens` (before 1.3.0 always null for OpenAI, as in all 2,510 records of the pilot's ledger); null when the provider gives none [57][59] |
| `model_requested`, `model_reported` | The model the client asked for and the one the provider reported |
| `cost`, `currency`, `reserve` | Cost computed from the usage and the configured prices; the amount reserved before forwarding |
| `voided`, `usage_missing`, `streamed`, `reserve_exceeded` | How the call ended (see the cap section) |
| `refusal`, `error` | The gateway's refusal code, or a short error code |
| `latency_ms`, `request_sha256`, `bytes_in`, `bytes_out` | Timing, and the hash and size of the body the client sent |
| `request_defaults_applied` | Names of what the gateway changed or added in the request: first a translation of the output-limit field if `translate_max_tokens` applied (version 1.2.0) [40], then the request-defaults fields, then the output-limit field if one was injected (see below) |

At every start the gateway also writes a manifest: its version, the hash of the config, the cap, and every model's prices with the page they were read from and the UTC time (`source_url`, `read_at`). Since version 1.1.0 it also holds each upstream's `allow_request_defaults` flag, each model's output limit, and the path of a key file, never the key; since version 1.2.0 it holds each model's `translate_max_tokens` flag [40]. A run therefore records where its numbers came from. `--summary LOGFILE` and a loopback endpoint return the same totals [3].

**Streaming** is passed through. For OpenAI chat the gateway asks for usage in the stream unless the client turned it off; for Anthropic it takes input from the start event and output from the last delta event [3].

### Where the usage fields come from

Both providers' field names were re-read for this page. Anthropic's documentation, read 20261102 19:39 UTC, says that a stream starts with a `message_start` event whose message carries `usage`, and that the token counts in the `usage` of `message_delta` events are "cumulative" [4]. Its prompt-caching page gives `total_input_tokens = cache_read_input_tokens + cache_creation_input_tokens + input_tokens`, and prices 5-minute cache writes at 1.25 times and 1-hour writes at 2 times the base input price. It prices cache reads at 0.1 times, with per-model exceptions listed in a table footnote [5]. The gateway takes one cached-read price and one cache-write price per model from its config, so these differences are the owner's input, not code [3].

OpenAI's documentation returned HTTP 403 to the fetch again (20261102 19:40 UTC). The primary source used instead is the `openai-python` type definitions on its `main` branch, which say they are generated from OpenAI's API specification (read 20261102 19:39 UTC) [6]. They give `usage.prompt_tokens` and `completion_tokens`; `prompt_tokens_details.cached_tokens` ("Cached tokens present in the prompt"); for embeddings only `prompt_tokens` and `total_tokens`; and, with `include_usage`, an extra final chunk with an empty `choices` list that carries the total, with a warning that an interrupted stream may lack it [6].

**One difference found on that read, and what it cost.** The same type definitions also list `prompt_tokens_details.cache_write_tokens`, "the unadjusted number of prompt tokens written to cache" (the field is in the files read on 20261102 20:12 UTC) [6]. The gateway read `cached_tokens` and did not read this field through version 1.2.0; its code was unchanged from `257c9d5` to `96d9007` [7][40][50]. OpenAI's answers carried both fields in `usage` in all four stages: 3,140,582 tokens reported as written over the 1,751 answers, 2,540,573 of them in stage D [57][58]. The gateway priced them as plain input, USD 0.10 per million. The model page and the prompt-caching guide, as the gateway's page records its reads of 20261103 (not re-read here), say that cache writes for the default 30-minute lifetime cost 1.25 times the uncached input rate, USD 0.125 for `gpt-6-luna`, and that `cached_tokens` "counts billed reads and excludes tokens charged as writes" [57]. At that price the four stages cost USD 1.18389, not the gateway's 1.10537, a difference of 0.07851 (7.1% of the gateway's total) [58]. **Whether OpenAI's bill follows the page was open until D-41.** The console lists cache writes as a line of their own (USD 0.275), and the archive now reads that line as fitting USD 0.125 per million (0.2751 at 0.125 for the calls beyond the complimentary allowance, where 0.10 would give 0.22), so the gateway's omission was of a billed category and the list-price total is 1.18389; the console's USD 0.67 is after complimentary tokens (above). That reading rests on the allowance fit (exact in completion order, 0.4% off on one line in start-time order), which I take as a fit and not a proof [64][65][76][77]. The earlier "Agrees" for stage A and for stages B and C were given against the gateway's figures; the results page does not know whether they covered dollars to the cent or tokens, so they neither confirm nor exclude the write price [58][60]. D-39 says the missing price was found after stage D, and version 1.3.0 prices it. The usage cannot tell a 30-minute write from OpenAI's 12-hour option, which costs twice as much; the pilot's requests did not ask for it, by the results page's list of the request keys in the body log [57][58].

### The cap and the refusal

Before forwarding, the gateway reserves the most the call could cost: the body size divided by an assumed minimum bytes per token, times the higher of the input and cache-write price, plus the maximum output times the output price. If spend so far plus open reservations plus this reserve would pass the cap, it answers HTTP 429 with the code `gateway_budget_exceeded` and forwards nothing. After the response, the reservation is replaced by the cost computed from the provider's usage fields. One lock covers the check, the reservation, the settlement and the log write [3].

| Outcome | Counted as |
|---|---|
| Success with usable usage | Cost from usage |
| Success with no usable usage, or a stream that never delivered it | The whole reservation, flagged `usage_missing` |
| The provider answers 401, 429, 500 or any non-2xx status | Zero, flagged `voided`; the provider's answer is passed through. Seen with a real provider only in stage A: a 401 recorded at zero and `voided`, and two 400s that cost nothing; the 1,740 chat requests of stages B to D all returned 200, and no 429 or 5xx ever came back [41][51][52][58][59] |
| Connection refused, closed or timed out before a response | Zero, `voided`; the client sees 502 or 504 |
| Refused by the gateway (cap, unpriced model, malformed request) | Zero; nothing forwarded; `refusal` is set |

The gateway does not start without a cap, without a price and a price source for every model, with an unknown key in its config, with a key file that is missing or unsafe, or with a key that is empty or looks pasted twice [3]. Since version 1.2.0 it also refuses to start when a model sets `translate_max_tokens` to something that is not a boolean, on an upstream that does not speak the OpenAI protocol, or on a paid upstream whose table lacks `allow_request_defaults` [40].

**What the cap does not guarantee.** It bounds spend as the gateway computes it, from configured prices and the provider's usage fields; it is not the provider's bill. In the pilot the two figures differ, as above (the gateway's total and the list-price total; the console's spend is after complimentary tokens). The reservation uses the higher of the input and the cache-write price, so it was not affected, and neither a stage limit nor the cap of USD 3.00 was near on either figure [57][58]. A call can cost more than its reservation when a request sets no output limit and the answer is long, when the input has more tokens than the bound assumed, or when a price is stale. The overshoot is recorded (`reserve_exceeded`), and later calls are refused. The plan therefore keeps a per-project spend limit at the provider as well [3]. A voided call is recorded at zero cost although a provider may still bill a generation it completed, for example one the gateway gave up on at the upstream timeout [3]. A call with no output limit, for a model that has no `output_limit_default`, is reserved at the config's `default_max_output_tokens`, which is 1,024 unless the config sets another value (the gateway's code and sample config say 1,024; the config text that the pass-A and hosted setups write sets 4,096); the default upstream timeout is 120 s (the pilot's profile sets 900); and the log holds no `finish_reason` and no reasoning-token count, which only the response body has (logged only with `log_bodies`) [22][3][7][26]. For these reasons the plan makes a hard limit at the provider a precondition of its first stage and adds a watchdog that reads the bodies [22]. The watchdog is built (below) [25]. The hard limit is the owner's action (decision 6 of the plan). Since `79bc3f4` the plan's header says the owner did it on 20261103: a project of its own at OpenAI with a USD 3 hard limit and a restricted key in a private file; D-43 records that the console showed the key's permissions as "All", which neither the plan nor the owner-steps page carries [83]. The files give the owner's reply "6 done, proceed" (D-34) and the steps page's recipe (monthly limit USD 3, hard limit on) as what lies behind that; none shows the setting, so it is the owner's report, not checked here [42][46]. The console, as D-40 records it, shows a limit of USD 5.00 beside the spend, against the plan's USD 3; whether that figure is the hard limit or a budget is unknown, and nothing was changed. Since `4a2fb67` the plan's header and the owner-steps page carry that note too [64][65][69][71]. OpenAI documents a project-level hard spend limit, but says that enforcement is not instantaneous and that recorded spend can slightly exceed the limit, so this limit is not exact either [37]. A dress rehearsal showed the same limit from the other side: the cap does not check what a provider reports (see the section on the dress rehearsal) [32]. A failed attempt carries no tokens in the log, so in a local run where attempts fail, token sums understate what the model server processed; call counts and statuses still include them [8].

### Opt-in request defaults

A per-model table of JSON fields the gateway adds to a request when the client did not send them. It exists because a local model that "thinks" unless asked not to cannot be asked by a builder: with the field `reasoning_effort` set to `"none"`, one test question took 0.3 s and 8 tokens instead of 17 s and 278 tokens (one question, one run each) [8][9]. Three limits keep it from distorting a paid run [3]:

- it is refused on any upstream that is not a local, no-key one, because a field added to a paid call can change what the call costs, **unless that upstream's own table sets `allow_request_defaults = true`** (version 1.1.0; before it the refusal had no exception). The flag belongs to one upstream, and the manifest records it;
- it may not set the model, the messages, the input, the stream, the stream options, `n` or any output limit, and the flag does not change that list;
- every call's record names the fields that were added, and the hash in the record is of the request as the client sent it; the body log keeps that request too, and the reservation is made from what was forwarded.

In stages A to D, OpenAI's `gpt-6-luna` accepted `reasoning_effort: "none"` added this way, and every answer reported 0 reasoning tokens and the finish reason `stop` (1,751 answered requests; for stages B to D the result files' response facts say so, run by run) [41][51][58].

**On a second backend.** The same table, with the same `reasoning_effort: "none"`, was used for the second local model, `gemma4:12b`, which Ollama installed as an MLX build while the first model runs on llama.cpp. On the same test question it gave 243 tokens by default and 10 with `"none"`, and 207 to 262 with `"low"`, `"medium"` or `"high"`; for that model only `"none"` was short (one question, one run each) [8]. The MLX runner also honours the model file's cap on answer length (two answers ended at exactly 6,144 tokens although LightRAG sends no `max_tokens`) and logged that structured output is unavailable, so builders that ask for a `response_format` were not run on it [8].

### What changed in the gateway for a paid run

The pass-B plan asked for two gateway changes before the first paid call (item F1 on the [X2 page](../x2-index-cost.md)) [22]. Commit `1e1b37c` (committed 20261102 21:12 UTC) made them and a third, and set the gateway's version to 1.1.0 [3][7][25]. Stage A then showed a fourth need, and commit `a446479` (committed 20261103 16:38:51 UTC) set the version to 1.2.0 [39][40]. Stage D's tables showed a fifth, and commit `dc58d11` (committed 20261103 19:14:09 UTC) set the version to 1.3.0 [56][57]:

| Addition | What it does | Why |
|---|---|---|
| `allow_request_defaults` (per upstream, default false) | Lets a model on a keyed upstream carry request defaults, as described above | A builder cannot send `reasoning_effort: "none"`, so for a paid model that reasons by default the gateway has to add it [3][25] |
| `output_limit_default` (per model, a positive whole number) | When a chat request carries neither `max_tokens` nor `max_completion_tokens` with a non-null value, the gateway writes the provider's own field (`max_completion_tokens` on an OpenAI-protocol upstream, `max_tokens` on an Anthropic one) before the reservation is computed, so the reservation uses it. A limit the client sent always wins; a `"max_tokens": null`, which fast-graphrag sends on summary calls, counts as not sent. The added field is named in `request_defaults_applied` | A call without a limit is reserved at the config's default and may cost more than that (recorded as `reserve_exceeded`); the plan injects 6,144 tokens, the value pass A used [3][22] |
| `key_file` (per upstream, in place of `key_env`) | The gateway opens a file itself. It must be a regular file that neither group nor others can read or write (mode 600 or stricter), at most 4 KiB, with one non-empty line. The key goes through the same shape check as an environment key and is redacted like it; the manifest holds the path, never the key | A runner script and the builders it starts, which may run in the runner's own process, then never hold the key. The plan's status section says this was added during the work [3][22] |
| `translate_max_tokens` (per model, default false; **version 1.2.0**, commit `a446479`) | On a chat request for that model, before the output limit is chosen: a `"max_tokens": null` is dropped (it then counts as not sent, so `output_limit_default` is injected if the model has one); a set `max_tokens` is renamed `max_completion_tokens` with the same value, which is then the client's own limit: it wins over `output_limit_default` and is what the reservation uses. A non-null `max_completion_tokens` beside a set `max_tokens` is refused (400 `gateway_bad_request`, nothing forwarded), because the gateway will not choose between them. Embeddings are never touched. It needs an upstream that speaks the OpenAI protocol and, on a paid one, `allow_request_defaults`. The record names the change first in `request_defaults_applied`: `max_tokens->max_completion_tokens` or `max_tokens(null)-dropped` | Stage A showed that `gpt-6-luna` rejects a set `max_tokens` (nano-graphrag sends 500 on entity summaries) and a `null` `max_tokens` (fast-graphrag's summaries) with a 400. The owner chose this labelled translation over recording both builders as incompatible or dropping them (D-35) [40][41][42] |
| OpenAI cache-write pricing (**version 1.3.0**, commit `dc58d11`) | On an OpenAI-protocol answer, `prompt_tokens_details.cache_write_tokens` is read as the call's cache-write count and priced at the model's `cache_write_per_mtok`, the key that Anthropic cache creation already used. A model with no such price is charged the writes as plain input, and the count is still recorded. The cost is the prompt less reads and writes at the input price, plus reads at the cached price, writes at the write price and the output. The record's `cache_creation_input_tokens` holds the count (before 1.3.0 always null for OpenAI). A null or missing figure counts as none. A figure that is not a count (a string, a fraction, a negative number, a boolean), or reads plus writes above `prompt_tokens`, makes the usage unusable: the call is charged its whole reservation and flagged `usage_missing`. A streamed usage chunk carries the writes the same way. No config key is new | Stage D's tables showed that every answer carried the field and that 1.2.0 priced the written tokens as plain input, about USD 0.079 below the figure with the model page's price (OPEN, as above) [57][58] |

The gateway's page gives an example for a paid pilot: an upstream with `key_file` and `allow_request_defaults = true`, and a model `gpt-6-luna` with `output_limit_default = 6144` and `reasoning_effort = "none"` as a request default. A builder that sends only a model and messages then reaches the provider with `max_completion_tokens: 6144` and `reasoning_effort: "none"` added, and the call is reserved at 6144 output tokens [3].

The translation is a departure from "the builder's request is forwarded as it is", and the gateway's page says that a user must say so wherever a result comes from a model that has it [40]. The profile carries the flag, the stage driver passes it to each run, the stage-A dry run prints whether it is on, and each result's `hosted` block records it and lists the departure [43]. The plan makes this the one exception to its rule that a rejected request shape is a result [41]. In stages B and C the flag was on in all 12 runs (each result's `hosted` block says so and lists the departure) and no call used it, so no call of B or C carried a `max_tokens`, set or null [51][52]. **In stage D one builder used it**: 13 of fast-graphrag's 96 requests carried `max_tokens: null`, the gateway dropped it and OpenAI answered each with 200 and `stop`. The ledger now names the translation in 15 records (my count): the two of stage A's re-test and these 13. Fourteen are `max_tokens(null)-dropped` and one is `max_tokens->max_completion_tokens`; it names no rename in stages B to D, so a set `max_tokens` (nano-graphrag's 500) has been renamed with a real provider only in stage A's re-test [58][59].

What stage A showed about the options is in the table under "What it has and has not met". The re-test through version 1.2.0 ran at 16:32 UTC and the commit that holds that version is at 16:38:51 UTC. The plan's run log now says which code ran: the working tree, whose gateway, `passb_common.py`, `passb_stage.py` and `passb_stage_a.py` were last changed, by file modification times, at 16:24 and 16:26, before the re-test, and no code file changed between the re-test and the commit `a446479` [39][46]. File times are not in git and the log records no hash of the code, so this is the archive's account, which this page could not check. The gateway page's list now says that `gpt-6-luna` accepted what the translation produces, in the re-test of three requests, all answered 200 [47]. `key_file` was exercised on macOS only: its permission check reads the mode bits of the open file, so it means nothing on a file system that does not keep modes, and it cannot see a copy of the key elsewhere, such as a backup [3].

### What it has and has not met

- **Met, against fakes and local models:** the real OpenAI and Anthropic SDKs, against fake providers on loopback [11]. Four builders, through the pass-A runners, in front of a local model server that speaks the OpenAI protocol and needs no key, with one local model; a second local model ran LightRAG only, on a different backend [8][12][3].
- **Met, since `40fe751`, against a fake paid upstream:** the four runners reproduce their rehearsals' calls and tokens through the hosted setup; the provider received the reasoning switch and the output limit on every chat call; a cap-exhausted run stopped with a recorded failure while the provider saw only the forwarded calls; a real watchdog ran beside a real gateway process and a fake provider [25]. The dress rehearsal ran the real stage driver, runners, builders, gateway and watchdog against a fake provider [32]. The stage-A script was run through a hosted gateway against the author's fake provider: 10 calls at USD 0.0016, the refusal test passed with one refused record and nothing forwarded, and the provider saw the reasoning switch on all 10 requests and the injected output limit on 9 (the tenth carries its own limit, which wins) [28].
- **Met, 20261103: one real provider, OpenAI's `gpt-6-luna`**: in the three stage-A runs (the stage-A script and the hosted gateway) and then, in stages B to D, the stage driver, the free pre-flight, the watchdog and the hosted setup of all four runners with their builders: 16 runs, 1,740 further chat requests answered, no rule tripped. Stage D added 20 documents for each builder, one run each (1,308 requests, the largest stage), and the first use of the labelled translation by a builder: 13 requests of fast-graphrag with a null `max_tokens`, all answered 200. Version 1.2.0 carried stages B to D; **version 1.3.0 has met no real provider**. The tables after this list have the details [40][41][50][51][56][58][59].

- **Not met:** the Anthropic route with any builder. Most builders speak the OpenAI protocol, so running one on an Anthropic model needs a provider-side compatibility layer or a translation in the gateway. The pass-B plan reads Anthropic's compatibility layer from its documentation: it accepts a `response_format` only as `json_schema` with `strict: true` and answers `json_object` with a 400, so fast-graphrag and nano-graphrag cannot run through it. Whether LightRAG and Microsoft GraphRAG run through it, and whether a gateway-added `thinking: {"type": "disabled"}` works there, is untested: **unstated** [1][3][22].
- **By design:** no authentication between client and gateway (any program of the owner's user on the Mac can spend the cap through it); the real key sits in the gateway process's environment, or, with a `key_file`, in a file the gateway reads; a gateway that is killed loses its open reservations, so the provider's own usage page must be checked after a crash; only three routes exist (chat completions, embeddings, messages) [3].
- **A residual risk of the key file, as the plan states it:** the file is readable by any process of the same user, including the builders, which run as that user. What is guaranteed is that the key is never handed to them (not in their environment, arguments, logs or results; the plan says its canary test checks this), not that a hostile builder could not open the file [22]. The gateway's page says it too (since the correction at `d824716`): the key is in the gateway process's memory, from the environment or from a `key_file`; a `key_file` is readable by any process of that user; the mode check refuses group and other access but does not check who owns the file; and that was not tested as root [3][28].
