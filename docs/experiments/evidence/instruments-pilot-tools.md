### The hosted setup for the four runners

`passb_common.py`, with an example profile `passb_profile.example.json` (commit `f4c28b2`, committed 20261102 22:08 UTC; plan item F2; changed by `a446479`, which added the optional `translate_max_tokens` flag). Each of the four pass-A runners takes `--hosted-profile PROFILE_JSON`; without the option a runner behaves as before [25][26].

- **The profile** is a JSON file with the prices and where they were read, the output limit, the request defaults, the upstream timeout, the run's allowance and the path of the key file, never a key. The example carries `gpt-6-luna`'s prices as the plan read them (USD 0.10 per million input tokens, 0.50 output, 0.01 cached input, 0.125 cache write; read 20261102 20:20 UTC), an output limit of 6144, `reasoning_effort: "none"`, a timeout of 900 s and an allowance of USD 0.10; its two paths are placeholders [26]. The write price was in the gateway's config in every pilot run (the result files' `hosted` block shows 0.125), but versions up to 1.2.0 applied it only to Anthropic's cache creation, so no OpenAI answer was priced with it [57][58]. Since `a446479` it also carries the optional flag `translate_max_tokens` (default false; the example sets it to `true`), which is written into the chat model's table in the gateway config [43]. It refuses a zero price [22].
- **Two upstreams.** The runner starts a gateway whose hosted upstream serves the chat model, with the key read from the file by the gateway alone (the gateway process is started with a minimal environment and no key on its command line), and whose local upstream serves the embedding model at price zero [26].
- **One ledger for the whole pilot.** The gateway is started with `--resume`. The cap in its config is the ledger's spend plus the run's allowance, so a run cannot take the ledger past what it was allowed, and a run reads only the lines it added [26][25].
- **The result file** gains a `hosted` block (cost, the model name as the provider reports it, never the key file's or the ledger's path) and a cost per checkpoint [25]. Since `a446479` the block also holds the flag and a list `departures_from_the_builders_requests`, which names the translation when it is on and is empty when it is off [43].

*Tested:* 49 unit tests (45 at `9885a3d`; `a446479` added four: the flag in the profile, in the config, and two calls through a fake paid upstream, with and without it; all 49 passed 20261103 16:42 UTC at `257c9d5`, in 19.2 s) [43][44]; 46 deliberate mutants of the module and 14 of the runner wiring, all killed [12]; the flag's copies in the profile, config and result block are among the 22 mutants of `a446479` (21 killed, the survivor equivalent) [40]. Against a fake paid upstream that answers with the stub rehearsals' responder, calls by kind and tokens at 1, 5 and 20 documents equal the committed rehearsals for all four runners; cost equals tokens times price; a distinctive fake key appears only in its key file, and in no environment, argument list, log, body log, manifest, result or output [25]. **Used against a real provider** through the stage-A script, whose `run` starts the same hosted gateway with the key read from the profile's key file, and, in stages B to D, by all four runners with `--hosted-profile` (16 runs; every result holds a `hosted` block with the model as the provider reports it, the flag and the departure) [27][41][43][51][58]. On the shared ledger a run's cap was the ledger's spend plus its allowance: for fast-graphrag's second run of stage C, 0.17133018 spent before plus an allowance of 0.47247483 gives the cap 0.64380501, and the result counts 27 calls (the ledger went from 497 to 524 records) [51]. *Not tested:* two runs on one ledger at the same time (not guarded in the module, because the plan runs builders one at a time); a builder sending a set `max_tokens` (nano-graphrag's 500) through the hosted path, with or without the translation: no call of stages B to D carried one, and only fast-graphrag's `null` went through the translation, in stage D [25][26][51][52][58][59].

### The free pre-flight

`passb_preflight.py` (commit `3657dab`, committed 21:40 UTC; item F4). It runs before each paid stage and before each run of a stage, given the stage, the builders and the ledger directory. It prints the expected tokens times price, the stage's limit and "stop at", what the ledger shows spent, the run's allowance and the cap to write into the gateway config; it exits with status 1 when the estimate does not fit [26][25]. The cap for the config is the spend so far plus the allowance, because a resumed gateway compares its cap with the whole log [22][26]. Its built-in tables are the plan's: `gpt-6-luna`'s prices, the total cap of USD 3.00, the stage limits 0.10, 0.20, 0.60 and 1.50, and a central token estimate per builder for stages B, C and D [26]. For one run of stages B, C and D it printed USD 0.0300, 0.1175 and 0.6252, equal to the assistant's own arithmetic [25]; the plan's stage C figure of 0.235 is two runs (0.1175 times 2, arithmetic) [22]. In stages B to D the driver ran it before each of the 16 runs, and its output set each run's allowance in the stage report: stage B's 0.2, then 0.19601168, 0.1920573 and 0.18138329 as the stage's spend grew, stage C's 0.6 falling the same way, and stage D's 1.5, then 1.41632594, 1.32943835 and 1.09859815; the table above compares its token estimates with the spend [51][58]. It has 54 unit tests, which passed again 20261103 16:44 UTC at `257c9d5` (0.6 s); the pre-flight is unchanged since `3657dab` [12][34][39][44].

### The watchdog

`passb_watchdog.py` (commit `3657dab`; item F7; changed by `90e8ae3`). It runs beside a paid stage and, every few seconds, reads what the gateway has appended to its log and its body log. It applies the plan's stop rules, eight in this order [26]:

| Rule | Trips when |
|---|---|
| Provider error | A status of 400 or above that is not a gateway refusal: a 429 or a 5xx is tolerated once per run, any other 4xx trips at once |
| Gateway refusal | Any record with a refusal |
| Usage missing | Any record flagged `usage_missing` |
| Reasoning tokens | Any chat response body with `reasoning_tokens` above zero in its usage details |
| Length stops | More than 5% of chat answers have the finish reason `length` |
| Repeated requests | More than 5% of the records in the repeat window (one run, see below) repeat an earlier request hash |
| Voided calls | More than 3 voided records |
| Spend | The summed cost passes the stage's "stop at" |

The defaults are the plan's percentages and count [26][22]. The code applies the two share rules only once at least 20 chat answers (length) or 20 records (repeats) have been seen, a minimum the plan's stop rules do not state; the plan's account of the dress rehearsal says it for the length rule, which stage B never reaches [26][32]. On a trip the watchdog writes a report of counts only, never body text, sends SIGTERM to the process groups and pids it was given, sends SIGKILL to survivors after a grace period of 10 s and exits with status 3. The `--since` option ignores records before a time, because one ledger is shared by all stages. The reasoning and length rules read response bodies, so they are blind unless the gateway runs with `log_bodies = true`; the watchdog counts the chat records that have no body and warns [26][25].

**The repeat window (`--repeat-since`, commit `90e8ae3`).** The rule against repeated requests is meant to catch a retry loop. As first written it counted a request as repeated if any earlier call of the stage had sent it. Stage C runs each builder twice on the same documents, so the second run sends the first run's requests again by design, and the dress rehearsal (below) stopped it within a second. Now records stamped before the run's start still count for every other rule, but their request hashes are not remembered and they are not in the repeat share's denominator. The plan's stop rule now reads "within one run", and the stage driver passes the run's start to the live watchdog and to its last read [31][32][30]. **Used live:** stage C's second run ran to the end for all four builders. The results page counts 0 repeated requests in every one of the 16 runs, and my count from the ledger agrees (0 of 2,496 records of the runs' windows). Counting any earlier request of the stage, as the rule first did, 10 to 16 records of each second run (12% to 59%) would have counted as repeats against the 5% allowed; 44 of the 168 chat requests of the four second runs carry the hash of a chat request of the same builder's first run, all 15 of fast-graphrag's among them (my counts) [51][52].

*Tested:* 92 unit tests (83 before the repeat window; all 92 passed again 20261103 16:44 UTC at `257c9d5`, in 7.3 s; the watchdog is unchanged since `90e8ae3`) [39][44]; 98 deliberate mutants of the watchdog and the pre-flight together, and 7 of the assistant's own, all killed, before the window; for the window, 9 more of the assistant's own, all killed (two survived until two tests pinned the share's denominator and the minimum sample) [33][34][25]. With a real gateway, a fake provider and a runner that has a child process, three clean calls were left alone, and a response with reasoning tokens made the watchdog exit with status 3 in 0.2 s, with the gateway, the runner and its child all gone and no response text or key in the report [25][12]. The dress rehearsal tripped it on 16 injected faults (below) [32]. *Used:* beside all 16 runs of stages B to D (the driver starts it for each run): no rule tripped, no kill, no process left, and the files do not record its polls [51][58]. Nothing in those runs was a fault (no provider error, refusal, missing usage, reasoning token, `length` stop or voided call in the ledger), so they show that it lets a normal run through, not that it would stop a real provider's fault; its trips have been exercised only against fakes [51][52][54]. *Not tested:* Linux; a trip beside a real runner under a real provider [25][33].

### The stage-A script

`passb_stage_a.py` with its test file (commit `15ccdea`, committed 20261102 22:53 UTC; plan item F3). Stage A is the first time the gateway meets a real provider: at most 12 calls and USD 0.10. The plan now says that both limits are per run of the script, not for the stage: three runs were made and 14 requests reached OpenAI in all (1 refused for the key, 10, 3), for USD 0.0065 against the 0.10; the pilot's USD 3 cap is the cumulative one [46]. The script has two subcommands and uses the standard library only; `a446479` changed it in one place, the dry run's printout, which now says whether the `max_tokens` translation is on [27][28][43].

- **`extract`** is free and local. It picks the first recorded request of each kind from pass A's gateway logs and adds requests written from the builders' source for the shapes pass A never logged, with dummy data and no article text (a ping, nano-graphrag's entity summary and community report, fast-graphrag's summary with `max_tokens: null`). At most 10 requests go to a JSON file of mode 600, which holds article text and which the program refuses to put inside the repository.
- **`run`** is a dry run unless `--send` is given: it prints the plan and the worst-case cost and starts nothing. With `--send` it checks the caps and the requests file, starts a hosted gateway, confirms from the gateway's summary that the cap it loaded is the cap computed, and only then sends each request once. It stops on an auth error, a gateway refusal, a missing usage object, a rejected ping or spend past USD 0.10; a 400 or 422 on any later request is recorded as the builder being incompatible, and the run goes on. It then sends the largest request to a second gateway with an allowance of USD 0.0001 and an upstream that nothing listens on, and requires a 429 refusal and a ledger with one record that holds no tokens, no cost and no void.
- **The result file** holds numbers, field names and short codes, never text, a key or a path, and the plan's gates as booleans. The program cannot read the provider's console, the one check the plan keeps independent of the gateway; it prints what to compare by hand.

### The stage driver

`passb_stage.py` with its example builders file `passb_builders.example.json` and a test file (commit `90e8ae3`, committed 20261103 00:25 UTC; plan item F8, which the plan added during the work; changed by `a446479`, so that the run profile it writes carries the `translate_max_tokens` flag [43]). It runs one stage (B with 1 document, C with 5, D with 20) for the builders named, one after another, and is the only thing to run for those stages. Without `--send` it is a dry run that starts and writes nothing [30][34].

For each builder, with `--send`, it does six things [30]:

1. It runs the free pre-flight; a refusal is written to the report and the program exits with status 1 before anything starts.
2. It writes a run profile (mode 600) that carries the pre-flight's allowance in place of the stage profile's own.
3. It starts the runner in its own session, with exactly the environment the builders file gives plus `PATH`, never its own.
4. It starts the watchdog beside it, with `--since` the stage's start (spend and counts are cumulative across the stage's runs) and `--repeat-since` this run's start.
5. When the runner ends it stops what the runner left behind and reads the stage's whole log once more with the same rules, so a call written just before the exit cannot slip past a poll.
6. It updates the stage report and the stage's state file with counts, rule names and times: no text from any request or response and no path outside the output directory.

A rule that fires stops the stage: the next builder is not started and the exit status is 3. A builder that fails by its own fault (the runner exits non-zero and no rule fired) is recorded as a result, and the next builder runs. The driver never opens the key file; only the gateway, started by the runner, reads it. The builders file lives outside the repository (the example holds placeholders): per builder, the interpreter, the runner, the environment and the extra flags. A variable name that looks like a credential is refused, and so is a profile, builders file, ledger or output directory inside the repository. A run label can be used once, and a lock on the ledger refuses a second driver on the same ledger [30].

*Tested:* 44 unit tests (43 at `9885a3d`; `a446479` added one, which checks that the run profile carries the flag; all 44 passed 20261103 16:43 UTC at `257c9d5`, in 39.7 s), with a fake runner script, the real gateway, pre-flight and watchdog, and a fake provider [30][43][44]. The builder made 52 deliberate mutants, all killed; the assistant made 34 after the repeat window was added, and 29 were killed. The five that were not: an unreachable zero-allowance branch and a lock descriptor the child never inherits (both equivalent), two timing constants, and a second signal arriving during clean-up [33][34]. The dress rehearsal below ran it with the real runners and builders. *Used* for stages B to D on 20261103: the stage report holds 16 entries, one per run (stage B for the four builders in the order LightRAG, fast-graphrag, Microsoft GraphRAG, nano-graphrag; stage C twice in that order; stage D once in that order), each with outcome `completed`, exit status 0, no tripped rule, no kill and no process left, from 17:19:26 to 19:01:30 UTC on the driver's clock (stage D from 17:57:54). None ended `tripped`, was refused by the pre-flight or failed by its own fault, so those paths have been run only against fakes [51][58]. D-37 covers stage D once, not a repeat [54][60]. *Not tested:* a SIGKILL of the driver (cannot be caught: the runner and the watchdog go on, and the watchdog still guards the runner). Two limits from its header: stages must be run in order, and after a trip the stage's window stays open, so to repeat the stage its state file is moved aside and a new run label used [30].

### The dress rehearsal

Run 20261102 23:48 to 23:58 UTC, free, nothing paid. Real: the stage driver, pre-flight, watchdog, gateway, the four runners and the four builders in their throwaway environments, with real processes, files, locks and signals. Fake: the paid provider (each builder's rehearsal answers, with fault modes) and the embedding server. A canary key stood in for the real one. The archive counts 573 checks in two groups [32][34]:

| Run | Checks | Result |
|---|---|---|
| The whole ladder for all four builders (16 runs): stage B, stage C twice, stage D, each after a dry run | 295 | All 16 runs completed; each run's spend equals its ledger rows to the last digit; the canary key is in no file outside its own and in no driver output; no process of a run was left |
| One injected fault per run, 16 runs (reasoning tokens; usage missing; dropped connections for all four builders; a bill beyond the allowance and a length stop for two builders) | 278 | Every run ended `tripped` with exit status 3, the rule named, the runner's whole group and its gateway stopped |

It found one design error and showed one limit, and it left some points unsettled [32]:

- **A design error, in the watchdog.** The repeat rule (above) stopped stage C's second run within a second. The archive reports that pass A's own ledgers confirm the premise: 23 of Microsoft GraphRAG's 103 five-document requests were identical to its one-document run's. No unit test had seen it, because the builder's fake runner never repeated itself. Decision D-31 records the change [32][33].
- **The cap does not check what a provider reports.** With a fake that reported 3,000 times the tokens a real output limit allows, two runs spent USD 1.18 (LightRAG) and 1.11 (Microsoft GraphRAG) against an allowance of USD 0.20, which is 5.6 to 5.9 times (my arithmetic; decision D-31 says "a factor of six") before the watchdog's next poll. The gateway reserves the worst case it believes and then charges what the provider says. The archive says a real provider cannot exceed the limit the gateway injected, so it does not expect this; it is why the hard limit at the provider (decision 6) stays the one independent guard [32][33].
- **What it could not settle.** The length rule is not evaluated below 20 chat answers, which stage B never reaches. A dropped connection tripped the provider-error rule, not the voided-calls rule, and was recorded at zero cost; a provider may still bill it, which the comparison with the console is for. The rehearsal could not show what a real provider accepts, its real token counts, its rate limits or its billing of failed calls [32]. Stages A to D have since shown part of it: what `gpt-6-luna` accepts and rejects among the builders' request shapes, real token counts for 1,751 answers, which usage fields a real answer carries (one of them a field the gateway did not read, `cache_write_tokens`, D-39) and that the repeat window lets stage C's second run through (above). Rate limits are still unseen (no 429 came at concurrency 4), and so is the billing of a call that fails after the provider began work: the only failed calls were stage A's three rejections [41][51][52][58].

Decision 3 rested on OpenAI's data page ("API data is not used for training unless you explicitly opt in"); on 20261104 the archive found the organisation's data-sharing setting ("Share inputs and outputs with OpenAI") on for all projects, so the pilot's article text and the models' outputs were probably shared with OpenAI for improving and training its models, which the plan did not assume, and the owner decided to leave the setting on (D-42); nothing was changed at OpenAI; since `6f59c99` the plan's decision-3 row and question 3 of the owner-steps page carry a marker to that effect [38][70][77].
