## The metering gateway

A small local HTTP proxy that every hosted [large language model](../index/large-language-model.md) call of an experiment passes through. It does three things the third-party builders cannot do themselves [3]:

1. It writes the provider's own usage fields into one common record, so a cost is measured, not estimated.
2. It refuses a call that could take spend past a cap, before anything is forwarded.
3. It keeps the real key. The code under test holds a dummy key and the gateway's address. The gateway reads the key itself, from its own environment or, since version 1.1.0, from a file only its owner can read.

It uses the standard library only, needs Python 3.11 or newer, and binds `127.0.0.1` and nothing else [3].

### What it records

One JSON line per call, written when the call ends. Money is a decimal string, never a float. Request bodies are not in this file [3].

| Field | Meaning |
|---|---|
| `input_tokens` | All prompt [tokens](../index/token.md), cached ones included. For Anthropic it is input plus cache read plus cache creation |
| `output_tokens` | Completion tokens; null when the provider gave no usage |
| `cached_input_tokens`, `cache_creation_input_tokens` | Cached prompt tokens; Anthropic cache writes; null when the provider gives none |
| `model_requested`, `model_reported` | The model the client asked for and the one the provider reported |
| `cost`, `currency`, `reserve` | Cost computed from the usage and the configured prices; the amount reserved before forwarding |
| `voided`, `usage_missing`, `streamed`, `reserve_exceeded` | How the call ended (see the cap section) |
| `refusal`, `error` | The gateway's refusal code, or a short error code |
| `latency_ms`, `request_sha256`, `bytes_in`, `bytes_out` | Timing, and the hash and size of the body the client sent |
| `request_defaults_applied` | Names of what the gateway changed or added in the request: first a translation of the output-limit field if `translate_max_tokens` applied (version 1.2.0) [40], then the request-defaults fields, then the output-limit field if one was injected (see below) |

At every start the gateway also writes a manifest: its version, the hash of the config, the cap, and every model's prices with the page they were read from and the UTC time (`source_url`, `read_at`). Since version 1.1.0 it also holds each upstream's `allow_request_defaults` flag, each model's output limit, and the path of a key file, never the key; since version 1.2.0 it holds each model's `translate_max_tokens` flag [40]. A run therefore records where its numbers came from. `--summary LOGFILE` and a loopback endpoint return the same totals [3].

**Streaming** is passed through. For OpenAI chat the gateway asks for usage in the stream unless the client turned it off; for Anthropic it takes input from the start event and output from the last delta event [3].

### Where the usage fields come from

Both providers' field names were re-read for this page. Anthropic's documentation, read 20261102 19:39 UTC, says that a stream starts with a `message_start` event whose message carries `usage`, and that the token counts in the `usage` of `message_delta` events are "cumulative" [4]. Its prompt-caching page gives `total_input_tokens = cache_read_input_tokens + cache_creation_input_tokens + input_tokens`, and prices 5-minute cache writes at 1.25 times and 1-hour writes at 2 times the base input price. It prices cache reads at 0.1 times, with per-model exceptions listed in a table footnote [5]. The gateway takes one cached-read price and one cache-write price per model from its config, so these differences are the owner's input, not code [3].

OpenAI's documentation returned HTTP 403 to the fetch again (20261102 19:40 UTC). The primary source used instead is the `openai-python` type definitions on its `main` branch, which say they are generated from OpenAI's API specification (read 20261102 19:39 UTC) [6]. They give `usage.prompt_tokens` and `completion_tokens`; `prompt_tokens_details.cached_tokens` ("Cached tokens present in the prompt"); for embeddings only `prompt_tokens` and `total_tokens`; and, with `include_usage`, an extra final chunk with an empty `choices` list that carries the total, with a warning that an interrupted stream may lack it [6].

**One difference found on this read.** The same type definitions now also list `prompt_tokens_details.cache_write_tokens`, "the unadjusted number of prompt tokens written to cache" [6]. The gateway reads `cached_tokens` and does not read this field, and still did not at `257c9d5` [7][40]. OpenAI's real answers in stage A carried both fields in `usage`; the values of `cache_write_tokens` are **unstated** in what was read [41]. Whether OpenAI prices such tokens differently is also **unstated**. The gateway's OpenAI cost does not separate them, so a difference would show in the comparison with the console, which the owner has still to make [41][42].

### The cap and the refusal

Before forwarding, the gateway reserves the most the call could cost: the body size divided by an assumed minimum bytes per token, times the higher of the input and cache-write price, plus the maximum output times the output price. If spend so far plus open reservations plus this reserve would pass the cap, it answers HTTP 429 with the code `gateway_budget_exceeded` and forwards nothing. After the response, the reservation is replaced by the cost computed from the provider's usage fields. One lock covers the check, the reservation, the settlement and the log write [3].

| Outcome | Counted as |
|---|---|
| Success with usable usage | Cost from usage |
| Success with no usable usage, or a stream that never delivered it | The whole reservation, flagged `usage_missing` |
| The provider answers 401, 429, 500 or any non-2xx status | Zero, flagged `voided`; the provider's answer is passed through. Seen once with a real provider: a 401 recorded at zero and `voided`, and two 400s that cost nothing [41] |
| Connection refused, closed or timed out before a response | Zero, `voided`; the client sees 502 or 504 |
| Refused by the gateway (cap, unpriced model, malformed request) | Zero; nothing forwarded; `refusal` is set |

The gateway does not start without a cap, without a price and a price source for every model, with an unknown key in its config, with a key file that is missing or unsafe, or with a key that is empty or looks pasted twice [3]. Since version 1.2.0 it also refuses to start when a model sets `translate_max_tokens` to something that is not a boolean, on an upstream that does not speak the OpenAI protocol, or on a paid upstream whose table lacks `allow_request_defaults` [40].

**What the cap does not guarantee.** It bounds spend as the gateway computes it, from configured prices and the provider's usage fields; it is not the provider's bill. A call can cost more than its reservation when a request sets no output limit and the answer is long, when the input has more tokens than the bound assumed, or when a price is stale. The overshoot is recorded (`reserve_exceeded`), and later calls are refused. The plan therefore keeps a per-project spend limit at the provider as well [3]. A voided call is recorded at zero cost although a provider may still bill a generation it completed, for example one the gateway gave up on at the upstream timeout [3]. A call with no output limit, for a model that has no `output_limit_default`, is reserved at the config's `default_max_output_tokens`, which is 1,024 unless the config sets another value (the gateway's code and sample config say 1,024; the config text that the pass-A and hosted setups write sets 4,096); the default upstream timeout is 120 s (the pilot's profile sets 900); and the log holds no `finish_reason` and no reasoning-token count, which only the response body has (logged only with `log_bodies`) [22][3][7][26]. For these reasons the plan makes a hard limit at the provider a precondition of its first stage and adds a watchdog that reads the bodies [22]. The watchdog is built (below) [25]. The hard limit is the owner's action (decision 6 of the plan): D-34 quotes the owner's reply "6 done, proceed", and the archive does not say what limit was set, so whether one exists is **unstated** [42]. OpenAI documents a project-level hard spend limit, but says that enforcement is not instantaneous and that recorded spend can slightly exceed the limit, so this limit is not exact either [37]. A dress rehearsal showed the same limit from the other side: the cap does not check what a provider reports (see the section on the dress rehearsal) [32]. A failed attempt carries no tokens in the log, so in a local run where attempts fail, token sums understate what the model server processed; call counts and statuses still include them [8].

### Opt-in request defaults

A per-model table of JSON fields the gateway adds to a request when the client did not send them. It exists because a local model that "thinks" unless asked not to cannot be asked by a builder: with the field `reasoning_effort` set to `"none"`, one test question took 0.3 s and 8 tokens instead of 17 s and 278 tokens (one question, one run each) [8][9]. Three limits keep it from distorting a paid run [3]:

- it is refused on any upstream that is not a local, no-key one, because a field added to a paid call can change what the call costs, **unless that upstream's own table sets `allow_request_defaults = true`** (version 1.1.0; before it the refusal had no exception). The flag belongs to one upstream, and the manifest records it;
- it may not set the model, the messages, the input, the stream, the stream options, `n` or any output limit, and the flag does not change that list;
- every call's record names the fields that were added, and the hash in the record is of the request as the client sent it; the body log keeps that request too, and the reservation is made from what was forwarded.

In stage A, OpenAI's `gpt-6-luna` accepted `reasoning_effort: "none"` added this way, and every answer reported 0 reasoning tokens and the finish reason `stop` [41].

**On a second backend.** The same table, with the same `reasoning_effort: "none"`, was used for the second local model, `gemma4:12b`, which Ollama installed as an MLX build while the first model runs on llama.cpp. On the same test question it gave 243 tokens by default and 10 with `"none"`, and 207 to 262 with `"low"`, `"medium"` or `"high"`; for that model only `"none"` was short (one question, one run each) [8]. The MLX runner also honours the model file's cap on answer length (two answers ended at exactly 6,144 tokens although LightRAG sends no `max_tokens`) and logged that structured output is unavailable, so builders that ask for a `response_format` were not run on it [8].

### What changed in the gateway for a paid run

The pass-B plan asked for two gateway changes before the first paid call (item F1 on the [X2 page](x2-index-cost.md)) [22]. Commit `1e1b37c` (committed 20261102 21:12 UTC) made them and a third, and set the gateway's version to 1.1.0 [3][7][25]. Stage A then showed a fourth need, and commit `a446479` (committed 20261103 16:38:51 UTC) set the version to 1.2.0 [39][40]:

| Addition | What it does | Why |
|---|---|---|
| `allow_request_defaults` (per upstream, default false) | Lets a model on a keyed upstream carry request defaults, as described above | A builder cannot send `reasoning_effort: "none"`, so for a paid model that reasons by default the gateway has to add it [3][25] |
| `output_limit_default` (per model, a positive whole number) | When a chat request carries neither `max_tokens` nor `max_completion_tokens` with a non-null value, the gateway writes the provider's own field (`max_completion_tokens` on an OpenAI-protocol upstream, `max_tokens` on an Anthropic one) before the reservation is computed, so the reservation uses it. A limit the client sent always wins; a `"max_tokens": null`, which fast-graphrag sends on summary calls, counts as not sent. The added field is named in `request_defaults_applied` | A call without a limit is reserved at the config's default and may cost more than that (recorded as `reserve_exceeded`); the plan injects 6,144 tokens, the value pass A used [3][22] |
| `key_file` (per upstream, in place of `key_env`) | The gateway opens a file itself. It must be a regular file that neither group nor others can read or write (mode 600 or stricter), at most 4 KiB, with one non-empty line. The key goes through the same shape check as an environment key and is redacted like it; the manifest holds the path, never the key | A runner script and the builders it starts, which may run in the runner's own process, then never hold the key. The plan's status section says this was added during the work [3][22] |
| `translate_max_tokens` (per model, default false; **version 1.2.0**, commit `a446479`) | On a chat request for that model, before the output limit is chosen: a `"max_tokens": null` is dropped (it then counts as not sent, so `output_limit_default` is injected if the model has one); a set `max_tokens` is renamed `max_completion_tokens` with the same value, which is then the client's own limit: it wins over `output_limit_default` and is what the reservation uses. A non-null `max_completion_tokens` beside a set `max_tokens` is refused (400 `gateway_bad_request`, nothing forwarded), because the gateway will not choose between them. Embeddings are never touched. It needs an upstream that speaks the OpenAI protocol and, on a paid one, `allow_request_defaults`. The record names the change first in `request_defaults_applied`: `max_tokens->max_completion_tokens` or `max_tokens(null)-dropped` | Stage A showed that `gpt-6-luna` rejects a set `max_tokens` (nano-graphrag sends 500 on entity summaries) and a `null` `max_tokens` (fast-graphrag's summaries) with a 400. The owner chose this labelled translation over recording both builders as incompatible or dropping them (D-35) [40][41][42] |

The translation is a departure from "the builder's request is forwarded as it is", and the gateway's page says that a user must say so wherever a result comes from a model that has it [40]. The plan makes this the one exception to its rule that a rejected request shape is a result [41].

### What it has and has not met

- **Met, against fakes and local models:** the real OpenAI and Anthropic SDKs, against fake providers on loopback [11]. Four builders, through the pass-A runners, in front of a local model server that speaks the OpenAI protocol and needs no key, with one local model; a second local model ran LightRAG only, on a different backend [8][12][3].
- **Met, since `40fe751`, against a fake paid upstream:** the four runners reproduce their rehearsals' calls and tokens through the hosted setup; the provider received the reasoning switch and the output limit on every chat call; a cap-exhausted run stopped with a recorded failure while the provider saw only the forwarded calls; a real watchdog ran beside a real gateway process and a fake provider [25]. The dress rehearsal ran the real stage driver, runners, builders, gateway and watchdog against a fake provider [32]. The stage-A script was run through a hosted gateway against the author's fake provider: 10 calls at USD 0.0016, the refusal test passed with one refused record and nothing forwarded, and the provider saw the reasoning switch on all 10 requests and the injected output limit on 9 (the tenth carries its own limit, which wins) [28].
- **Met, 20261103: one real provider, OpenAI's `gpt-6-luna`**, in the three stage-A runs; the table after this list has the details [40][41].
- **Not met, even with OpenAI:** streaming, the embeddings route, a 429 or 5xx from the provider, an upstream timeout, and OpenAI's own billing: the comparison of its usage page with the gateway's total (11 answered requests, 16,945 input tokens of which 2,043 cached, 9,893 output, USD 0.00645713) is the owner's and was pending [40][41][42]. No builder has run end to end through a real provider; stages B to D have not started [42].
- **Not met:** Anthropic's real servers. Their wire formats are those of the documentation above, not of an observed response; a field or status that differs would show as `usage_missing` or a voided call [3][22].
- **Not met:** the Anthropic route with any builder. Most builders speak the OpenAI protocol, so running one on an Anthropic model needs a provider-side compatibility layer or a translation in the gateway. The pass-B plan reads Anthropic's compatibility layer from its documentation: it accepts a `response_format` only as `json_schema` with `strict: true` and answers `json_object` with a 400, so fast-graphrag and nano-graphrag cannot run through it. Whether LightRAG and Microsoft GraphRAG run through it, and whether a gateway-added `thinking: {"type": "disabled"}` works there, is untested: **unstated** [1][3][22].
- **By design:** no authentication between client and gateway (any program of the owner's user on the Mac can spend the cap through it); the real key sits in the gateway process's environment, or, with a `key_file`, in a file the gateway reads; a gateway that is killed loses its open reservations, so the provider's own usage page must be checked after a crash; only three routes exist (chat completions, embeddings, messages) [3].
- **A residual risk of the key file, as the plan states it:** the file is readable by any process of the same user, including the builders, which run as that user. What is guaranteed is that the key is never handed to them (not in their environment, arguments, logs or results; the plan says its canary test checks this), not that a hostile builder could not open the file [22]. The gateway's page says it too (since the correction at `d824716`): the key is in the gateway process's memory, from the environment or from a `key_file`; a `key_file` is readable by any process of that user; the mode check refuses group and other access but does not check who owns the file; and that was not tested as root [3][28].

## The stub model server

A loopback server that speaks the OpenAI chat and [embeddings](../index/embedding.md) protocols, needs no key and reaches nothing beyond `127.0.0.1`. A builder is pointed at it instead of a model; it records every call and answers with whatever a responder function returns. It therefore counts a builder's calls and prompt sizes for given documents without spending anything [13].

What it can and cannot show is stated in its own header. Prompt sizes and any call count that does not depend on what the model says are exact for the given input. Anything driven by the output (gleaning loops, retries, summaries triggered by growing descriptions, community reports) is a count for the responder's answers only. Token counts use a public tokenizer (`cl100k_base`) or characters divided by four, neither of which is any provider's own [13]. Pass A later showed how far this can be from a real model: one local model wrote 4.1 to 14.7 times the stub's output tokens in the three builders that indexed a document, and Microsoft GraphRAG made 27 chat calls where the stub run made 9, on one document each. At 5 documents the ratios were 4.2 to 15.9 for the three builders that got there, and the second local model wrote 6.9 times the stub's output on LightRAG [8].

Eight tests pass (run 20261103 16:44 UTC at `257c9d5`, in 3.0 s; the stub's last commit is `8edc27c`, committed 20261102 10:24 UTC) [10][39][44]. The archive records that one failed on first run because the listen queue held 5 and a burst of 20 parallel calls was undercounted; the queue is now 256 and breaking that on purpose turns the test red [14].

## The statistics helper

Four functions for the later comparisons, standard library only [15]:

| Function | Computes |
|---|---|
| `paired_counts` | The questions only one of two runs got right |
| `sign_test` | The exact two-sided p-value for those pairs, under "each discordant pair is a fair coin" |
| `wilson` | A Wilson interval for a proportion |
| `bootstrap_mean_diff` | A seeded, paired, percentile bootstrap of a mean difference |

Its header says what it does not do: it says nothing about whether a comparison is fair, whether questions are independent, or whether the sample is large enough to matter [15]. Seventeen tests pass (run 20261103 16:44 UTC at `257c9d5`; the helper's last commit is `f64ad55`, committed 20261102 10:29 UTC), each checked in the archive record against an independent oracle such as brute-force enumeration [10][14][39][44].

## The frozen sets

### X2: twenty documents

The rule was fixed before the result was looked at and involves no choice: rank every article of the [MultiHop-RAG](../datasets/multihop-rag.md) corpus (a news dataset for [multi-hop question answering](../index/multi-hop-question-answering.md)) by the SHA-256 of its URL and keep the 20 smallest. The selection tool refuses a corpus file whose hash differs from the pinned one [16].

Re-checked for this page: the corpus file at the pinned Hugging Face revision hashes to the pinned value (`20b61b5a...e4d28f`), and running the selection tool on it reproduces the committed list of 20 rows byte for byte (20261102 19:38 UTC) [17]. The article text is never committed, because the news text comes from publishers whose own terms were not checked; only identifiers and sizes are [14]. ### The hosted setup for the four runners

`passb_common.py`, with an example profile `passb_profile.example.json` (commit `f4c28b2`, committed 20261102 22:08 UTC; plan item F2; changed by `a446479`, which added the optional `translate_max_tokens` flag). Each of the four pass-A runners takes `--hosted-profile PROFILE_JSON`; without the option a runner behaves as before [25][26].

- **The profile** is a JSON file with the prices and where they were read, the output limit, the request defaults, the upstream timeout, the run's allowance and the path of the key file, never a key. The example carries `gpt-6-luna`'s prices as the plan read them (USD 0.10 per million input tokens, 0.50 output, 0.01 cached input, 0.125 cache write; read 20261102 20:20 UTC), an output limit of 6144, `reasoning_effort: "none"`, a timeout of 900 s and an allowance of USD 0.10; its two paths are placeholders [26]. It refuses a zero price [22].
- **Two upstreams.** The runner starts a gateway whose hosted upstream serves the chat model, with the key read from the file by the gateway alone (the gateway process is started with a minimal environment and no key on its command line), and whose local upstream serves the embedding model at price zero [26].

### The watchdog

`passb_watchdog.py` (commit `3657dab`; item F7; changed by `90e8ae3`). It runs beside a paid stage and, every few seconds, reads what the gateway has appended to its log and its body log. It applies the plan's stop rules, eight in this order [26]:

| Rule | Trips when |
|---|---|
| Provider error | A status of 400 or above that is not a gateway refusal: a 429 or a 5xx is tolerated once per run, any other 4xx trips at once |
| Gateway refusal | Any record with a refusal |
| Usage missing | Any record flagged `usage_missing` |
| Reasoning tokens | Any chat response body with `reasoning_tokens` above zero in its usage details |
| Length stops | More than 5% of chat answers have the finish reason `length` |
| Repeated requests | More than 5% of the records in the repeat window (one run, see below) repeat an earlier request hash |
| Voided calls | More than 3 voided records |
| Spend | The summed cost passes the stage's "stop at" |

The defaults are the plan's percentages and count [26][22]. The code applies the two share rules only once at least 20 chat answers (length) or 20 records (repeats) have been seen, a minimum the plan's stop rules do not state; the plan's account of the dress rehearsal says it for the length rule, which stage B never reaches [26][32]. On a trip the watchdog writes a report of counts only, never body text, sends SIGTERM to the process groups and pids it was given, sends SIGKILL to survivors after a grace period of 10 s and exits with status 3. The `--since` option ignores records before a time, because one ledger is shared by all stages. The reasoning and length rules read response bodies, so they are blind unless the gateway runs with `log_bodies = true`; the watchdog counts the chat records that have no body and warns [26][25].

**The repeat window (`--repeat-since`, commit `90e8ae3`).** The rule against repeated requests is meant to catch a retry loop. As first written it counted a request as repeated if any earlier call of the stage had sent it. Stage C runs each builder twice on the same documents, so the second run sends the first run's requests again by design, and the dress rehearsal (below) stopped it within a second. Now records stamped before the run's start still count for every other rule, but their request hashes are not remembered and they are not in the repeat share's denominator. The plan's stop rule now reads "within one run", and the stage driver passes the run's start to the live watchdog and to its last read [31][32][30].

*Tested:* 92 unit tests (83 before the repeat window; all 92 passed again 20261103 16:44 UTC at `257c9d5`, in 7.3 s; the watchdog is unchanged since `90e8ae3`) [39][44]; 98 deliberate mutants of the watchdog and the pre-flight together, and 7 of the assistant's own, all killed, before the window; for the window, 9 more of the assistant's own, all killed (two survived until two tests pinned the share's denominator and the minimum sample) [33][34][25]. With a real gateway, a fake provider and a runner that has a child process, three clean calls were left alone, and a response with reasoning tokens made the watchdog exit with status 3 in 0.2 s, with the gateway, the runner and its child all gone and no response text or key in the report [25][12]. The dress rehearsal tripped it on 16 injected faults (below) [32]. *Not tested:* Linux; the watchdog beside a real runner of a builder under a real provider [25][33].

### The stage driver

`passb_stage.py` with its example builders file `passb_builders.example.json` and a test file (commit `90e8ae3`, committed 20261103 00:25 UTC; plan item F8, which the plan added during the work; changed by `a446479`, so that the run profile it writes carries the `translate_max_tokens` flag [43]). It runs one stage (B with 1 document, C with 5, D with 20) for the builders named, one after another, and is the only thing to run for those stages. Without `--send` it is a dry run that starts and writes nothing [30][34].

For each builder, with `--send`, it does six things [30]:

1. It runs the free pre-flight; a refusal is written to the report and the program exits with status 1 before anything starts.
2. It writes a run profile (mode 600) that carries the pre-flight's allowance in place of the stage profile's own.
3. It starts the runner in its own session, with exactly the environment the builders file gives plus `PATH`, never its own.
4. It starts the watchdog beside it, with `--since` the stage's start (spend and counts are cumulative across the stage's runs) and `--repeat-since` this run's start.
5. When the runner ends it stops what the runner left behind and reads the stage's whole log once more with the same rules, so a call written just before the exit cannot slip past a poll.
6. It updates the stage report and the stage's state file with counts, rule names and times: no text from any request or response and no path outside the output directory.

A rule that fires stops the stage: the next builder is not started and the exit status is 3. A builder that fails by its own fault (the runner exits non-zero and no rule fired) is recorded as a result, and the next builder runs. The driver never opens the key file; only the gateway, started by the runner, reads it. The builders file lives outside the repository (the example holds placeholders): per builder, the interpreter, the runner, the environment and the extra flags. A variable name that looks like a credential is refused, and so is a profile, builders file, ledger or output directory inside the repository. A run label can be used once, and a lock on the ledger refuses a second driver on the same ledger [30].

*Tested:* 44 unit tests (43 at `9885a3d`; `a446479` added one, which checks that the run profile carries the flag; all 44 passed 20261103 16:43 UTC at `257c9d5`, in 39.7 s), with a fake runner script, the real gateway, pre-flight and watchdog, and a fake provider [30][43][44]. The builder made 52 deliberate mutants, all killed; the assistant made 34 after the repeat window was added, and 29 were killed. The five that were not: an unreachable zero-allowance branch and a lock descriptor the child never inherits (both equivalent), two timing constants, and a second signal arriving during clean-up [33][34]. The dress rehearsal below ran it with the real runners and builders. *Not used* in a real stage, which has not started: stage B waits for the console comparison [42]. *Not tested:* a SIGKILL of the driver (cannot be caught: the runner and the watchdog go on, and the watchdog still guards the runner). Two limits from its header: stages must be run in order, and after a trip the stage's window stays open, so to repeat the stage its state file is moved aside and a new run label used [30].
