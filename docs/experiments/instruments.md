## The metering gateway

A small local HTTP proxy that every hosted [large language model](../index/large-language-model.md) call of an experiment passes through. It does three things the third-party builders cannot do themselves [3]:

1. It writes the provider's own usage fields into one common record, so a cost is measured, not estimated.
2. It refuses a call that could take spend past a cap, before anything is forwarded.
3. It keeps the real key. The code under test holds a dummy key and the gateway's address. The gateway reads the key itself, from its own environment or, since version 1.1.0, from a file only its owner can read.

It uses the standard library only, needs Python 3.11 or newer, and binds `127.0.0.1` and nothing else [3]. Its version at `5f0c5d2` is 1.3.0 (the code is as at `c960df7`). Stages B to D ran on 1.2.0, and no real provider has met 1.3.0 [57][58][63].

### What it records

One JSON line per call, written when the call ends. Money is a decimal string, never a float. Request bodies are not in this file [3].

| Field | Meaning |
|---|---|
| `input_tokens` | All prompt [tokens](../index/token.md), cached ones included. For Anthropic it is input plus cache read plus cache creation |
| `output_tokens` | Completion tokens; null when the provider gave no usage |
| `cached_input_tokens`, `cache_creation_input_tokens` | Cached prompt tokens (reads); cache writes: Anthropic's `cache_creation_input_tokens` and, from 1.3.0, OpenAI's `prompt_tokens_details.cache_write_tokens` (before 1.3.0 always null for OpenAI, as in all 2,510 records of the pilot's ledger); null when the provider gives none [57][59] |
| `model_requested`, `model_reported` | The model the client asked for and the one the provider reported |
| `cost`, `currency`, `reserve` | Cost computed from the usage and the configured prices; the amount reserved before forwarding |
| `voided`, `usage_missing`, `streamed`, `reserve_exceeded` | How the call ended (see the cap section) |
| `refusal`, `error` | The gateway's refusal code, or a short error code |
| `latency_ms`, `request_sha256`, `bytes_in`, `bytes_out` | Timing, and the hash and size of the body the client sent |
| `request_defaults_applied` | Names of what the gateway changed or added in the request: first a translation of the output-limit field if `translate_max_tokens` applied (version 1.2.0) [40], then the request-defaults fields, then the output-limit field if one was injected (see below) |

At every start the gateway also writes a manifest: its version, the hash of the config, the cap, and every model's prices with the page they were read from and the UTC time (`source_url`, `read_at`). Since version 1.1.0 it also holds each upstream's `allow_request_defaults` flag, each model's output limit, and the path of a key file, never the key; since version 1.2.0 it holds each model's `translate_max_tokens` flag [40]. A run therefore records where its numbers came from. `--summary LOGFILE` and a loopback endpoint return the same totals [3].

**Streaming** is passed through. For OpenAI chat the gateway asks for usage in the stream unless the client turned it off; for Anthropic it takes input from the start event and output from the last delta event [3].

### Where the usage fields come from

Both providers' field names were re-read for this page. Anthropic's documentation, read 20261102 19:39 UTC, says that a stream starts with a `message_start` event whose message carries `usage`, and that the token counts in the `usage` of `message_delta` events are "cumulative" [4]. Its prompt-caching page gives `total_input_tokens = cache_read_input_tokens + cache_creation_input_tokens + input_tokens`, and prices 5-minute cache writes at 1.25 times and 1-hour writes at 2 times the base input price. It prices cache reads at 0.1 times, with per-model exceptions listed in a table footnote [5]. The gateway takes one cached-read price and one cache-write price per model from its config, so these differences are the owner's input, not code [3].

OpenAI's documentation returned HTTP 403 to the fetch again (20261102 19:40 UTC). The primary source used instead is the `openai-python` type definitions on its `main` branch, which say they are generated from OpenAI's API specification (read 20261102 19:39 UTC) [6]. They give `usage.prompt_tokens` and `completion_tokens`; `prompt_tokens_details.cached_tokens` ("Cached tokens present in the prompt"); for embeddings only `prompt_tokens` and `total_tokens`; and, with `include_usage`, an extra final chunk with an empty `choices` list that carries the total, with a warning that an interrupted stream may lack it [6].

**One difference found on that read, and what it cost.** The same type definitions also list `prompt_tokens_details.cache_write_tokens`, "the unadjusted number of prompt tokens written to cache" (the field is in the files read on 20261102 20:12 UTC) [6]. The gateway read `cached_tokens` and did not read this field through version 1.2.0; its code was unchanged from `257c9d5` to `96d9007` [7][40][50]. OpenAI's answers carried both fields in `usage` in all four stages: 3,140,582 tokens reported as written over the 1,751 answers, 2,540,573 of them in stage D [57][58]. The gateway priced them as plain input, USD 0.10 per million. The model page and the prompt-caching guide, as the gateway's page records its reads of 20261103 (not re-read here), say that cache writes for the default 30-minute lifetime cost 1.25 times the uncached input rate, USD 0.125 for `gpt-6-luna`, and that `cached_tokens` "counts billed reads and excludes tokens charged as writes" [57]. At that price the four stages cost USD 1.18389, not the gateway's 1.10537, a difference of 0.07851 (7.1% of the gateway's total) [58]. **Whether OpenAI's bill follows the page was open until D-41.** The console lists cache writes as a line of their own (USD 0.275), and the archive now reads that line as fitting USD 0.125 per million (0.2751 at 0.125 for the calls beyond the complimentary allowance, where 0.10 would give 0.22), so the gateway's omission was of a billed category and the list-price total is 1.18389; the console's USD 0.67 is after complimentary tokens (above). That reading rests on the allowance fit, which I take as a fit and not a proof [64][65][70][71]. The earlier "Agrees" for stage A and for stages B and C were given against the gateway's figures; the results page does not know whether they covered dollars to the cent or tokens, so they neither confirm nor exclude the write price [58][60]. D-39 says the missing price was found after stage D, and version 1.3.0 prices it. The usage cannot tell a 30-minute write from OpenAI's 12-hour option, which costs twice as much; the pilot's requests did not ask for it, by the results page's list of the request keys in the body log [57][58].

### The cap and the refusal

Before forwarding, the gateway reserves the most the call could cost: the body size divided by an assumed minimum bytes per token, times the higher of the input and cache-write price, plus the maximum output times the output price. If spend so far plus open reservations plus this reserve would pass the cap, it answers HTTP 429 with the code `gateway_budget_exceeded` and forwards nothing. After the response, the reservation is replaced by the cost computed from the provider's usage fields. One lock covers the check, the reservation, the settlement and the log write [3].

| Outcome | Counted as |
|---|---|
| Success with usable usage | Cost from usage |
| Success with no usable usage, or a stream that never delivered it | The whole reservation, flagged `usage_missing` |
| The provider answers 401, 429, 500 or any non-2xx status | Zero, flagged `voided`; the provider's answer is passed through. Seen with a real provider only in stage A: a 401 recorded at zero and `voided`, and two 400s that cost nothing; the 1,740 chat requests of stages B to D all returned 200, and no 429 or 5xx ever came back [41][51][52][58][59] |
| Connection refused, closed or timed out before a response | Zero, `voided`; the client sees 502 or 504 |
| Refused by the gateway (cap, unpriced model, malformed request) | Zero; nothing forwarded; `refusal` is set |

The gateway does not start without a cap, without a price and a price source for every model, with an unknown key in its config, with a key file that is missing or unsafe, or with a key that is empty or looks pasted twice [3]. Since version 1.2.0 it also refuses to start when a model sets `translate_max_tokens` to something that is not a boolean, on an upstream that does not speak the OpenAI protocol, or on a paid upstream whose table lacks `allow_request_defaults` [40].

**What the cap does not guarantee.** It bounds spend as the gateway computes it, from configured prices and the provider's usage fields; it is not the provider's bill. In the pilot the two figures differ, as above (the gateway's total and the list-price total; the console's spend is after complimentary tokens). The reservation uses the higher of the input and the cache-write price, so it was not affected, and neither a stage limit nor the cap of USD 3.00 was near on either figure [57][58]. A call can cost more than its reservation when a request sets no output limit and the answer is long, when the input has more tokens than the bound assumed, or when a price is stale. The overshoot is recorded (`reserve_exceeded`), and later calls are refused. The plan therefore keeps a per-project spend limit at the provider as well [3]. A voided call is recorded at zero cost although a provider may still bill a generation it completed, for example one the gateway gave up on at the upstream timeout [3]. A call with no output limit, for a model that has no `output_limit_default`, is reserved at the config's `default_max_output_tokens`, which is 1,024 unless the config sets another value (the gateway's code and sample config say 1,024; the config text that the pass-A and hosted setups write sets 4,096); the default upstream timeout is 120 s (the pilot's profile sets 900); and the log holds no `finish_reason` and no reasoning-token count, which only the response body has (logged only with `log_bodies`) [22][3][7][26]. For these reasons the plan makes a hard limit at the provider a precondition of its first stage and adds a watchdog that reads the bodies [22]. The watchdog is built (below) [25]. The hard limit is the owner's action (decision 6 of the plan). Since `79bc3f4` the plan's header says the owner did it on 20261103: a project of its own at OpenAI with a USD 3 hard limit and a restricted key in a private file. The files give the owner's reply "6 done, proceed" (D-34) and the steps page's recipe (monthly limit USD 3, hard limit on) as what lies behind that; none shows the setting, so it is the owner's report, not checked here [42][46]. The console, as D-40 records it, shows a limit of USD 5.00 beside the spend, against the plan's USD 3; whether that figure is the hard limit or a budget is unknown, and nothing was changed. Since `4a2fb67` the plan's header and the owner-steps page carry that note too [64][65][69][71]. OpenAI documents a project-level hard spend limit, but says that enforcement is not instantaneous and that recorded spend can slightly exceed the limit, so this limit is not exact either [37]. A dress rehearsal showed the same limit from the other side: the cap does not check what a provider reports (see the section on the dress rehearsal) [32]. A failed attempt carries no tokens in the log, so in a local run where attempts fail, token sums understate what the model server processed; call counts and statuses still include them [8].

### Opt-in request defaults

A per-model table of JSON fields the gateway adds to a request when the client did not send them. It exists because a local model that "thinks" unless asked not to cannot be asked by a builder: with the field `reasoning_effort` set to `"none"`, one test question took 0.3 s and 8 tokens instead of 17 s and 278 tokens (one question, one run each) [8][9]. Three limits keep it from distorting a paid run [3]:

- it is refused on any upstream that is not a local, no-key one, because a field added to a paid call can change what the call costs, **unless that upstream's own table sets `allow_request_defaults = true`** (version 1.1.0; before it the refusal had no exception). The flag belongs to one upstream, and the manifest records it;
- it may not set the model, the messages, the input, the stream, the stream options, `n` or any output limit, and the flag does not change that list;
- every call's record names the fields that were added, and the hash in the record is of the request as the client sent it; the body log keeps that request too, and the reservation is made from what was forwarded.

In stages A to D, OpenAI's `gpt-6-luna` accepted `reasoning_effort: "none"` added this way, and every answer reported 0 reasoning tokens and the finish reason `stop` (1,751 answered requests; for stages B to D the result files' response facts say so, run by run) [41][51][58].

**On a second backend.** The same table, with the same `reasoning_effort: "none"`, was used for the second local model, `gemma4:12b`, which Ollama installed as an MLX build while the first model runs on llama.cpp. On the same test question it gave 243 tokens by default and 10 with `"none"`, and 207 to 262 with `"low"`, `"medium"` or `"high"`; for that model only `"none"` was short (one question, one run each) [8]. The MLX runner also honours the model file's cap on answer length (two answers ended at exactly 6,144 tokens although LightRAG sends no `max_tokens`) and logged that structured output is unavailable, so builders that ask for a `response_format` were not run on it [8].

A limit the client sent always wins; a `"max_tokens": null`, which fast-graphrag sends on summary calls, counts as not sent. | `key_file` (per upstream, in place of `key_env`) | The gateway opens a file itself. ## The stub model server

A loopback server that speaks the OpenAI chat and [embeddings](../index/embedding.md) protocols, needs no key and reaches nothing beyond `127.0.0.1`. A builder is pointed at it instead of a model; it records every call and answers with whatever a responder function returns. It therefore counts a builder's calls and prompt sizes for given documents without spending anything [13].

What it can and cannot show is stated in its own header. Prompt sizes and any call count that does not depend on what the model says are exact for the given input. Anything driven by the output (gleaning loops, retries, summaries triggered by growing descriptions, community reports) is a count for the responder's answers only. Token counts use a public tokenizer (`cl100k_base`) or characters divided by four, neither of which is any provider's own [13]. Pass A later showed how far this can be from a real model: one local model wrote 4.1 to 14.7 times the stub's output tokens in the three builders that indexed a document, and Microsoft GraphRAG made 27 chat calls where the stub run made 9, on one document each. At 5 documents the ratios were 4.2 to 15.9 for the three builders that got there, and the second local model wrote 6.9 times the stub's output on LightRAG [8].

Eight tests pass (run 20261103 16:44 UTC at `257c9d5`, in 3.0 s; the stub's last commit is `8edc27c`, committed 20261102 10:24 UTC) [10][39][44]. The archive records that one failed on first run because the listen queue held 5 and a burst of 20 parallel calls was undercounted; the queue is now 256 and breaking that on purpose turns the test red [14].

### The watchdog

`passb_watchdog.py` (commit `3657dab`; item F7; changed by `90e8ae3`). It runs beside a paid stage and, every few seconds, reads what the gateway has appended to its log and its body log. It applies the plan's stop rules, eight in this order [26]:

| Rule | Trips when |
|---|---|
| Provider error | A status of 400 or above that is not a gateway refusal: a 429 or a 5xx is tolerated once per run, any other 4xx trips at once |
| Gateway refusal | Any record with a refusal |
| Usage missing | Any record flagged `usage_missing` |
| Reasoning tokens | Any chat response body with `reasoning_tokens` above zero in its usage details |
| Length stops | More than 5% of chat answers have the finish reason `length` |
| Repeated requests | More than 5% of the records in the repeat window (one run, see below) repeat an earlier request hash |
| Voided calls | More than 3 voided records |
| Spend | The summed cost passes the stage's "stop at" |

The defaults are the plan's percentages and count [26][22]. The code applies the two share rules only once at least 20 chat answers (length) or 20 records (repeats) have been seen, a minimum the plan's stop rules do not state; the plan's account of the dress rehearsal says it for the length rule, which stage B never reaches [26][32]. On a trip the watchdog writes a report of counts only, never body text, sends SIGTERM to the process groups and pids it was given, sends SIGKILL to survivors after a grace period of 10 s and exits with status 3. The `--since` option ignores records before a time, because one ledger is shared by all stages. The reasoning and length rules read response bodies, so they are blind unless the gateway runs with `log_bodies = true`; the watchdog counts the chat records that have no body and warns [26][25].

**The repeat window (`--repeat-since`, commit `90e8ae3`).** The rule against repeated requests is meant to catch a retry loop. As first written it counted a request as repeated if any earlier call of the stage had sent it. Stage C runs each builder twice on the same documents, so the second run sends the first run's requests again by design, and the dress rehearsal (below) stopped it within a second. Now records stamped before the run's start still count for every other rule, but their request hashes are not remembered and they are not in the repeat share's denominator. The plan's stop rule now reads "within one run", and the stage driver passes the run's start to the live watchdog and to its last read [31][32][30]. **Used live:** stage C's second run ran to the end for all four builders. The results page counts 0 repeated requests in every one of the 16 runs, and my count from the ledger agrees (0 of 2,496 records of the runs' windows). Counting any earlier request of the stage, as the rule first did, 10 to 16 records of each second run (12% to 59%) would have counted as repeats against the 5% allowed; 44 of the 168 chat requests of the four second runs carry the hash of a chat request of the same builder's first run, all 15 of fast-graphrag's among them (my counts) [51][52].

*Tested:* 92 unit tests (83 before the repeat window; all 92 passed again 20261103 16:44 UTC at `257c9d5`, in 7.3 s; the watchdog is unchanged since `90e8ae3`) [39][44]; 98 deliberate mutants of the watchdog and the pre-flight together, and 7 of the assistant's own, all killed, before the window; for the window, 9 more of the assistant's own, all killed (two survived until two tests pinned the share's denominator and the minimum sample) [33][34][25]. With a real gateway, a fake provider and a runner that has a child process, three clean calls were left alone, and a response with reasoning tokens made the watchdog exit with status 3 in 0.2 s, with the gateway, the runner and its child all gone and no response text or key in the report [25][12]. The dress rehearsal tripped it on 16 injected faults (below) [32]. *Used:* beside all 16 runs of stages B to D (the driver starts it for each run): no rule tripped, no kill, no process left, and the files do not record its polls [51][58]. Nothing in those runs was a fault (no provider error, refusal, missing usage, reasoning token, `length` stop or voided call in the ledger), so they show that it lets a normal run through, not that it would stop a real provider's fault; its trips have been exercised only against fakes [51][52][54]. *Not tested:* Linux; a trip beside a real runner under a real provider [25][33].

### The stage driver

`passb_stage.py` with its example builders file `passb_builders.example.json` and a test file (commit `90e8ae3`, committed 20261103 00:25 UTC; plan item F8, which the plan added during the work; changed by `a446479`, so that the run profile it writes carries the `translate_max_tokens` flag [43]). It runs one stage (B with 1 document, C with 5, D with 20) for the builders named, one after another, and is the only thing to run for those stages. Without `--send` it is a dry run that starts and writes nothing [30][34].

For each builder, with `--send`, it does six things [30]:

1. It runs the free pre-flight; a refusal is written to the report and the program exits with status 1 before anything starts.
2. It writes a run profile (mode 600) that carries the pre-flight's allowance in place of the stage profile's own.
3. It starts the runner in its own session, with exactly the environment the builders file gives plus `PATH`, never its own.
4. It starts the watchdog beside it, with `--since` the stage's start (spend and counts are cumulative across the stage's runs) and `--repeat-since` this run's start.
5. When the runner ends it stops what the runner left behind and reads the stage's whole log once more with the same rules, so a call written just before the exit cannot slip past a poll.
6. It updates the stage report and the stage's state file with counts, rule names and times: no text from any request or response and no path outside the output directory.

A rule that fires stops the stage: the next builder is not started and the exit status is 3. A builder that fails by its own fault (the runner exits non-zero and no rule fired) is recorded as a result, and the next builder runs. The driver never opens the key file; only the gateway, started by the runner, reads it. The builders file lives outside the repository (the example holds placeholders): per builder, the interpreter, the runner, the environment and the extra flags. A variable name that looks like a credential is refused, and so is a profile, builders file, ledger or output directory inside the repository. A run label can be used once, and a lock on the ledger refuses a second driver on the same ledger [30].

*Tested:* 44 unit tests (43 at `9885a3d`; `a446479` added one, which checks that the run profile carries the flag; all 44 passed 20261103 16:43 UTC at `257c9d5`, in 39.7 s), with a fake runner script, the real gateway, pre-flight and watchdog, and a fake provider [30][43][44].
